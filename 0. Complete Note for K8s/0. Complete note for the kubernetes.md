# LESSON 0 — Kubernetes Setup (Local PC / Kali Linux + VPS)

## 0.1 Kubernetes কী? Docker-এর সাথে সম্পর্ক

**English:** Docker runs containers on ONE machine. Kubernetes (K8s) runs containers across MANY machines — it restarts crashed containers, scales them under load, distributes them across servers, and rolls out updates without downtime.

**বাংলা:** Docker একটি machine-এ container চালায়। Kubernetes অনেক machine জুড়ে container চালায় — crash হলে restart করে, load বাড়লে scale করে, সব server-এ ছড়িয়ে দেয়, downtime ছাড়া update করে।

### Architecture (এক নজরে)

```text
┌──────────────── KUBERNETES CLUSTER ────────────────┐
│                                                     │
│  ┌──────── Control Plane (Master Node) ────────┐    │
│  │  kube-apiserver   ← kubectl এখানে কথা বলে     │    │
│  │  etcd             ← cluster-এর সব data-এর DB   │    │
│  │  kube-scheduler   ← কোন pod কোন node-এ যাবে    │    │
│  │  controller-mgr   ← desired state ঠিক রাখে     │    │
│  └──────────────────────────────────────────────┘    │
│                      │                              │
│        ┌─────────────┼─────────────┐                │
│        ▼             ▼             ▼                │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │ Worker 1 │  │ Worker 2 │  │ Worker 3 │           │
│  │ kubelet  │  │ kubelet  │  │ kubelet  │ ← master-এর│
│  │kube-proxy│  │kube-proxy│  │kube-proxy│   আদেশ শোনে │
│  │ pods 🟢🟢 │  │ pods 🟢  │  │ pods 🟢🟢│           │
│  └──────────┘  └──────────┘  └──────────┘           │
└─────────────────────────────────────────────────────┘
```

| Component | কাজ (বাংলা) |
|---|---|
| `kube-apiserver` | Cluster-এর দরজা — সব command (kubectl) এখান দিয়েই যায় |
| `etcd` | Cluster-এর সব তথ্য (কী চলছে, কোথায়) জমা থাকে — distributed database |
| `kube-scheduler` | নতুন pod কোন worker node-এ বসবে ঠিক করে |
| `controller-manager` | চায় ৩টি pod, চলছে ২টি → আরেকটি বানায় (desired state বজায় রাখে) |
| `kubelet` | প্রতিটি worker-এ থাকে — master-এর আদেশে pod চালু/বন্ধ করে |
| `kube-proxy` | Worker-এর network traffic ঘুরায় (service → pod) |

## 0.2 Local PC (Kali/Parrot/Debian) Setup — ৪টি Tool

**আপনার note অনুযায়ী — Docker, Minikube, kubectl, Helm এই ৪টিই minimum:**

```bash
# ─── 1. Docker (আগে থেকেই লাগবে) ───
sudo apt update
sudo apt install docker.io -y
sudo usermod -aG docker $USER
# logout/login করুন

# ─── 2. Minikube ───
curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube_latest_amd64.deb
sudo dpkg -i minikube_latest_amd64.deb

# ─── 3. kubectl (⚠️ Kali/Parrot-এ apt-এ পাওয়া যায় না — official binary নামান) ───
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
chmod +x kubectl
sudo mv kubectl /usr/local/bin/
kubectl version --client

# ─── 4. Helm ───
curl https://raw.githubusercontent.com/helm/helm/master/scripts/get-helm-3 | bash
helm version
```

| Tool | কেন দরকার |
|---|---|
| Docker | Minikube-এর driver — node-গুলো Docker container হিসেবে চলে |
| Minikube | Local-এ mini Kubernetes cluster চালায় |
| kubectl | Kubernetes-এর সাথে কথা বলার CLI — **এটিই আপনার প্রধান হাতিয়ার** |
| Helm | Kubernetes-এর package manager (Lesson 5) |

> ⚠️ **Kali/Parrot টিপ:** `sudo apt install kubectl` কাজ করে না — official binary method-ই ব্যবহার করুন (উপরে দেওয়া)। Snap version পুরোনো হয়, avoid করুন।

# LESSON 1 — Namespace + মূল Concept

## 1.1 Namespace কী?

**English:** A namespace is like a folder that holds ONE complete project — all its pods, deployments, services, configs, and secrets live inside it. One project = one namespace. In Docker Swarm you had one `docker-stack.yml` per project (laravel stack: nginx, mysql, phpmyadmin...); in Kubernetes, that whole stack lives under ONE namespace.

**বাংলা:** Namespace হলো folder-এর মতো — একটি পুরো project-এর সব কিছু (pods, deployment, service, config, secrets) তার ভিতরে থাকে। **১ project = ১ namespace।** Docker Swarm-এ একটি project-এর জন্য একটি `docker-stack.yml` ছিল (laravel stack: nginx, mysql, phpmyadmin...); Kubernetes-এ সেই পুরো stack-ই থাকে একটি namespace-এর ভিতরে।

```text
Kubernetes Cluster
├── namespace: ostad          ← project 1 (সব resource এখানে)
│     ├── pods
│     ├── deployment
│     ├── service
│     └── configmap + secrets
├── namespace: laravel-app    ← project 2
└── namespace: kube-system    ← Kubernetes-এর নিজের জিনিস (ছোঁবেন না!)
```

## 1.2 Namespace Commands (Class Cheatsheet)

```bash
kubectl get ns                        # সব namespace দেখা
kubectl get ns -A                     # একই কাজ (-A = all)
kubectl create ns ostad               # namespace বানানো
kubectl delete ns ostad               # namespace মোছা (⚠️ ভিতরের সব resource-ও যাবে!)
kubectl describe ns ostad             # namespace-এর বিস্তারিত
```

### নির্দিষ্ট namespace-এ কাজ করা

```bash
kubectl get pods -n ostad             # ostad namespace-এর pod-গুলো
kubectl get svc -n ostad              # service (svc = service-এর short name)
kubectl get deploy -n ostad           # deployment
kubectl apply -f file.yml -n ostad    # YAML apply করা নির্দিষ্ট namespace-এ

# বারবার -n লেখার ঝামেলা বাঁচাতে — default namespace set করে দিন:
kubectl config set-context --current --namespace=ostad

# এখন -n ছাড়াই সব ostad-এ চলবে; বর্তমান namespace দেখতে:
kubectl config view --minify | grep namespace:
```

### সব namespace জুড়ে দেখা

```bash
kubectl get pods -A                   # সব namespace-এর pod
kubectl get svc -A                    # সব namespace-এর service
kubectl get deploy -A                 # সব namespace-এর deployment
kubectl get events -A                 # সব event (debug-এর জন্য খুব দরকারি!)
```

| Command | ব্যাখ্যা |
|---|---|
| `-n ostad` | একটি command-এর জন্য namespace বেছে নেওয়া |
| `set-context --current --namespace=ostad` | Terminal session-এর default বদলে দেওয়া — daily life-এর সেরা সময়-বাঁচানো trick |
| `kubectl get events -A` | Cluster-এ কী ঘটছে (pod create, fail, pull error) — **debug করার প্রথম জায়গা** |

> 💡 **YAML-এও namespace দেওয়া যায়:** `metadata:`-এর নিচে `namespace: ostad` লিখলে `-n` flag ছাড়াই সঠিক জায়গায় যাবে।

# LESSON 2 — Pod, Deployment, Service

## 2.1 Pod — সবচেয়ে ছোট একক

**English:** A Pod is the smallest unit in Kubernetes — a wrapper around your container(s). You rarely create pods directly; but understanding them first makes Deployment clear.

**বাংলা:** Pod হলো Kubernetes-এর সবচেয়ে ছোট একক — আপনার container-এর চারপাশের মোড়ক। সরাসরি pod কম বানানো হয়, কিন্তু এটি বুঝলে Deployment পরিষ্কার হয়।

### `create_pods.yml`

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
  - name: nginx-container
    image: nginx:latest
    ports:
    - containerPort: 80
```

### Line-by-Line ব্যাখ্যা

| Line | English | বাংলা |
|---|---|---|
| `apiVersion: v1` | Which Kubernetes API version to use (rule of writing YAML) | YAML লেখার নিয়ম — কোন API version ব্যবহার হবে |
| `kind: Pod` | Resource type — Pod, Deployment, Service, etc. | কোন resource বানাচ্ছেন তা declare করা |
| `metadata:` | Description/information about the resource | Resource-এর পরিচয় অংশ |
| `name: nginx-pod` | Name of this pod | Pod-এর নাম |
| `labels: app: nginx` | Tag on the pod — OTHER resources (service/deployment) find this pod by this label | Pod-এর ট্যাগ — অন্য resource (service/deployment) এই label দিয়ে pod-কে খুঁজবে |
| `spec:` | Specification — what should run | কী চলবে তার বিবরণ |
| `containers:` | List of containers in this pod (usually one) | Pod-এর ভিতরের container-এর তালিকা |
| `name: nginx-container` | Container name | Container-এর নাম |
| `image: nginx:latest` | Image from Docker Hub/local | Docker Hub/local থেকে image |
| `containerPort: 80` | Container runs on port 80 (host will use another port, e.g. 8080) | Container-এর ভিতরে ৮০ port — host-এ অন্য port (যেমন 8080) দিয়ে access করবেন (Docker-এর বাম:ডান rule মনে আছে?) |

### চালানো ও দেখা

```bash
kubectl apply -f create_pods.yml -n ostad    # pod তৈরি
kubectl get pods -n ostad                    # দেখা

# Output:
# NAME        READY   STATUS    RESTARTS   AGE
# nginx-pod   1/1     Running   0          62s
```

## 2.2 Port-Forward — Pod-কে Browser-এ দেখা

```bash
kubectl port-forward pod/nginx-pod 8080:80 -n ostad
# Forwarding from 127.0.0.1:8080 -> 80
```

Browser-এ: `http://localhost:8080`

| Part | ব্যাখ্যা |
|---|---|
| `8080:80` | Docker-এর মতোই rule: **বাম = আপনার PC (host), ডান = container** — 2.1 (Docker book) মনে আছে? |
| `port-forward` | আপনার PC-এর port-কে pod-এর port-এর সাথে জুড়ে দেয় — terminal বন্ধ করলে সংযোগও বন্ধ |

> ⚠️ **সমস্যা:** প্রতিবার manually port-forward করা ঝামেলার। তাই আমরা **Deployment** (replica + auto-healing) ও **Service** (স্থায়ী port-forward-এর মতো কাজ করে) ব্যবহার করি — নিচেই।

## 2.3 Deployment — Replica + Auto-Healing

**English:** A Deployment manages ReplicaSets and ensures your desired number of pods are ALWAYS running. A pod dies? Deployment recreates it. Want 5 copies? Change one number.

**বাংলা:** Deployment নিশ্চিত করে আপনার চাওয়া সংখ্যক pod **সবসময়** চলছে। Pod মরে গেলে? Deployment নতুন বানায়। ৫টি copy চান? একটি সংখ্যা বদলান।

### `create_deployment.yml`

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx-container
          image: nginx:latest
          ports:
            - containerPort: 80
```

### Line-by-Line ব্যাখ্যা

| Line | English | বাংলা |
|---|---|---|
| `apiVersion: apps/v1` | Stable API for Deployment, ReplicaSet, StatefulSet (Pod ছিল `v1`) | Deployment-এর API version — Pod-এর চেয়ে আলাদা |
| `kind: Deployment` | This resource is a Deployment | Resource type = Deployment |
| `replicas: 3` | 3 pod copies must ALWAYS run | ৩টি pod copy সবসময় চলতে হবে |
| `selector: matchLabels: app: nginx` | WHICH pods this Deployment controls — pods having label `app: nginx` | Deployment কোন pod-গুলোকে manage করবে — যাদের label `app: nginx` |
| `template:` | Blueprint for creating pods | Pod বানানোর ছাঁচ/নকশা |
| `template.metadata.labels: app: nginx` | Pods created from this template get this label — **MUST match selector** | এই ছাঁচ থেকে বানানো pod-রা এই label পাবে — **selector-এর সাথে অবশ্যই মিলতে হবে**, না মিললে error |
| `template.spec.containers:` | Same container spec as a Pod | Pod-এর মতোই container-এর বিবরণ |

### চালানো ও যাচাই

```bash
kubectl apply -f create_deployment.yml -n ostad

kubectl get deployment -n ostad
# NAME               READY   UP-TO-DATE   AVAILABLE   AGE
# nginx-deployment   3/3     3            3           64s

kubectl get pods -n ostad
# nginx-deployment-6586c5b5fb-2cl8l   1/1   Running
# nginx-deployment-6586c5b5fb-rtl9j   1/1   Running
# nginx-deployment-6586c5b5fb-wtfkm   1/1   Running

kubectl get rs -n ostad      # ReplicaSet দেখুন
# nginx-deployment-6586c5b5fb   3   3   3
```

| Concept | ব্যাখ্যা |
|---|---|
| Deployment → ReplicaSet → Pod | Chain: Deployment ReplicaSet বানায়, ReplicaSet pod বানায়। `rs` = ReplicaSet-এর short name |
| Pod-এর নামে random অংশ | `6586c5b5fb` = ReplicaSet-এর hash, শেষের `2cl8l` = pod-এর random id — pod মরে নতুন হলে নাম বদলে যায় |
| **Self-healing test** | `kubectl delete pod <name> -n ostad` করুন — দেখবেন সাথে সাথে নতুন pod তৈরি হচ্ছে! এটাই Docker Swarm-এর replica-এর K8s রূপ |

## 2.4 Service — স্থায়ী Access (port-forward-এর বিকল্প)

**English:** Pods die and get new IPs/names. A Service gives a STABLE address that always forwards traffic to the right pods — matching them by label.

**বাংলা:** Pod মরে নতুন IP/নাম পায়। Service একটি **স্থায়ী address** দেয় যা সবসময় সঠিক pod-এ traffic পাঠায় — label মিলিয়ে pod খুঁজে নেয়।

### `create_service.yml`

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
  namespace: ostad
  labels:
    app: nginx
spec:
  type: NodePort
  selector:
    app: nginx
  ports:
    - protocol: TCP
      port: 8080
      targetPort: 80
```

### Line-by-Line ব্যাখ্যা

| Line | English | বাংলা |
|---|---|---|
| `kind: Service` | This resource is a Service | Resource type = Service |
| `namespace: ostad` | Created inside the ostad namespace | ostad namespace-এ তৈরি হবে |
| `type: NodePort` | Exposes on a port of every node — works locally without extra setup | প্রতিটি node-এর একটি port-এ খোলে — local-এ ঝামেলা ছাড়াই কাজ করে |
| `selector: app: nginx` | Connects this service to pods with label `app: nginx` — **must match** pod/deployment labels | Label `app: nginx`-ওয়ালা pod-দের সাথে জোড়া লাগায় — pod/deployment-এর label-এর সাথে **মিলতে হবে** |
| `protocol: TCP` | Traffic protocol | Traffic-এর protocol |
| `port: 8080` | Service-এর নিজের port (cluster-এর ভিতরে) | Cluster-এর ভিতরে service এই port-এ শোনে |
| `targetPort: 80` | Forwards to THIS port on the pod (containerPort) | Pod-এর কোন port-এ traffic যাবে (containerPort) |

### Service Type — ৩ ধরনের (পরীক্ষা ও কাজে খুব দরকারি)

| Type | কী | কোথায় ব্যবহার |
|---|---|---|
| `ClusterIP` (default) | শুধু cluster-এর **ভিতরে** access — বাইরে থেকে নয় | app → database (internal) |
| `NodePort` | প্রতিটি node-এর `<NodeIP>:<nodePort>`-এ খোলে | Local/minikube-এ test |
| `LoadBalancer` | Cloud-এ external IP পায়; minikube-এ `minikube tunnel` লাগে | Production (cloud) |

### Minikube-এ Service দেখা

```bash
kubectl apply -f create_service.yml
kubectl get svc -n ostad

# NodePort type হলে:
minikube service nginx-service -n ostad     # সরাসরি browser-এ খুলে দেয়!

# LoadBalancer type ব্যবহার করলে আগে tunnel লাগবে:
minikube tunnel                             # আলাদা terminal-এ চালু রাখুন
kubectl get svc -n ostad                    # এখন EXTERNAL-IP দেখাবে
```

| Command | ব্যাখ্যা |
|---|---|
| `minikube service <name>` | Minikube-এর সেরা shortcut — সঠিক IP:port নিয়ে browser খুলে দেয় |
| `minikube tunnel` | LoadBalancer type-কে local-এ external IP দেয় (terminal-এ চালু রাখতে হয়) |

> 🎯 **মনে রাখার সূত্র:** Pod = কাজ করে, Deployment = pod বাঁচিয়ে রাখে, Service = pod-কে খুঁজে পাওয়ার ঠিকানা। আর তিনটিকে জোড়া লাগায় — **label/selector** (Lesson 4)।

# LESSON 3 — ConfigMap, Secrets & Volume

## 3.1 ConfigMap vs Secret — কোনটা কখন?

| | ConfigMap (short: `cm`) | Secret |
|---|---|---|
| কী রাখে | সাধারণ env variable (password-জাতীয় নয়) | Password, token, APP_KEY-জাতীয় গোপন তথ্য |
| উদাহরণ | `DEBUG: "true"`, `APP_ENV: production` | `DB_PASSWORD`, `AWS_SECRET` |
| কীভাবে জমা | Plain text | Base64 encoded (⚠️ encryption নয়, শুধু encoding!) |
| Docker-এর সমতুল্য | `.env`-এর non-secret অংশ | `.env`-এর secret অংশ / Docker secret |

## 3.2 ConfigMap তৈরি

### `configMap.yml`

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config
data:
  DEBUG: "true"
```

```bash
kubectl apply -f configMap.yml -n ostad
kubectl get cm -n ostad              # cm = configmap-এর short name
kubectl describe cm nginx-config -n ostad
kubectl delete cm nginx-config -n ostad
```

## 3.3 Secret তৈরি

### `secrets.yml`

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: nginx-secret
type: Opaque
data:
  username: dXNlcm5hbWU=
  password: cGFzc3dvcmQ=
```

| Line | ব্যাখ্যা |
|---|---|
| `type: Opaque` | Default generic type — বেশিরভাগ কাজে এটিই যথেষ্ট |
| `dXNlcm5hbWU=` | `username` শব্দের base64 encoded রূপ |

**Base64 encode/decode (terminal-এ):**

```bash
echo -n "username" | base64            # encode: dXNlcm5hbWU=
echo "dXNlcm5hbWU=" | base64 -d        # decode: username
```

**Command দিয়েই Secret বানানো (YAML ছাড়া — সহজ পদ্ধতি):**

```bash
kubectl create secret generic my-secret \
  --from-literal=username=admin \
  --from-literal=password=secret123 -n ostad
```

> ⚠️ **গুরুত্বপূর্ণ:** Base64 = encryption **নয়** — যে keu decode করতে পারে। তাই secret YAML কখনোই public git-এ দেবেন না। Production-এ RBAC + encryption at rest/Sealed Secrets ব্যবহার করুন।

## 3.4 Deployment-এ ব্যবহার — ৩টি পদ্ধতি

### পদ্ধতি ১: সরাসরি `env` (ছোট মানের জন্য)

```yaml
spec:
  containers:
  - name: nginx-container
    image: nginx:latest
    env:
    - name: ENVIRONMENT
      value: "production"
    - name: APP_VERSION
      value: "v1"
```

### পদ্ধতি ২: `envFrom` — পুরো ConfigMap/Secret একসাথে (সবচেয়ে সহজ)

```yaml
spec:
  containers:
  - name: nginx-container
    image: nginx:latest
    envFrom:
    - configMapRef:
        name: nginx-config        # ConfigMap-এর সব key env variable হয়ে যাবে
    - secretRef:
        name: nginx-secret        # Secret-এর সব key env variable হয়ে যাবে
```

| Line | ব্যাখ্যা |
|---|---|
| `envFrom` | ফাইলের **সব** key-value একসাথে env variable হিসেবে ঢোকে — ডট Docker-এর `--env-file`-এর মতো |
| `configMapRef: name:` | কোন ConfigMap থেকে নেবে (metadata-এর name) |
| `secretRef: name:` | কোন Secret থেকে নেবে |

### পদ্ধতি ৩: একটি নির্দিষ্ট key নেওয়া (`valueFrom`)

```yaml
    env:
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: nginx-secret      # কোন secret
          key: password           # তার কোন key
```

## 3.5 Volume Mount — ConfigMap-কে File হিসেবে Container-এ ঢোকানো

**English:** env variable-এর বদলে ConfigMap-এর content-কে সরাসরি **file** হিসেবে container-এর ভিতরে রাখা — যেমন nginx config file।

**বাংলা:** env variable না দিয়ে ConfigMap-এর content সরাসরি **file** হিসেবে container-এর ভিতরে বসানো — যেমন nginx-এর config file।

### দুইটি অংশ বুঝুন (আপনার note-এর স্টাইলে)

```yaml
spec:
  template:
    spec:
      containers:
      - name: nginx-container
        image: nginx:latest
        # ── অংশ A: ভিতরে কোথায় বসবে ──
        volumeMounts:
        - name: config-volume          # volume-এর নাম (নিচের volumes-এর সাথে মিলতে হবে)
          mountPath: /etc/nginx/conf.d # container-এর ভিতরের কোন folder-এ বসবে

      # ── অংশ B: কী জিনিস ঢোকবে ──
      volumes:
      - name: config-volume            # উপরের volumeMounts-এর name-এর সাথে মিলবে
        configMap:
          name: nginx-config           # কোন ConfigMap file হিসেবে যাবে
```

| অংশ | প্রশ্নের উত্তর দেয় | ব্যাখ্যা |
|---|---|---|
| `volumeMounts` (container-এর ভিতরে) | **কোথায় বসবে?** | Container-এর ভিতরের path — ConfigMap-এর প্রতিটি key একটি file হয়ে এই folder-এ বসবে |
| `volumes` (pod level-এ) | **কী বসবে?** | Source — কোন ConfigMap/Secret/PVC থেকে আসবে |
| দুটোর `name` একই | জোড়া লাগানো | `config-volume` নামটিই দুই অংশকে যুক্ত করে |

### ConfigMap-এ file content রাখা (যেমন nginx config)

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config
data:
  default.conf: |
    server {
        listen 80;
        root /var/www/html;
    }
```

| Line | ব্যাখ্যা |
|---|---|
| `default.conf: \|` | `\|` = multi-line text — এই key-এর নামেই container-এ file তৈরি হবে (`/etc/nginx/conf.d/default.conf`) |

> 🎯 **ফলাফল:** Container-এর ভিতরে `/etc/nginx/conf.d/default.conf` file থাকবে, যার content ConfigMap থেকে এসেছে। ConfigMap update করে pod restart দিলেই নতুন config — image rebuild লাগে না!

# LESSON 4 — Kind vs Kubeadm vs Minikube + Labels & Selectors

## 4.1 তিনটি Tool-এর পার্থক্য (পরীক্ষায় ও কাজে খুব আসে)

```text
┌────────────────┬─────────────────────┬─────────────────────┐
│      KIND      │      KUBEADM        │      MINIKUBE       │
├────────────────┼─────────────────────┼─────────────────────┤
│ K8s চলে Docker │ Real server/VM-এ    │ Laptop-এ হালকা       │
│ container-এ    │ আসল cluster install │ single-node cluster  │
├────────────────┼─────────────────────┼─────────────────────┤
│ CI/CD, দ্রুত   │ Production-grade    │ শেখা, development    │
│ test           │ real multi-node     │ নতুন feature try     │
├────────────────┼─────────────────────┼─────────────────────┤
│ খুব হালকা,     │ ভারী — আসল machine  │ মাঝারি — VM/Docker   │
│ VM লাগে না     │ লাগে                │ driver ব্যবহার করে   │
├────────────────┼─────────────────────┼─────────────────────┤
│ Production নয় │ Production হ্যাঁ     │ Production নয়       │
└────────────────┴─────────────────────┴─────────────────────┘
```

| Tool | উদ্দেশ্য | Node | কখন ব্যবহার |
|---|---|---|---|
| **Kind** | Kubernetes **IN** Docker | Docker container-ই node (fake) | দ্রুত test, CI/CD pipeline |
| **kubeadm** | Real cluster install করার tool | আসল server/VM | **VPS-এ production cluster** (Lesson 6) |
| **Minikube** | Mini Kubernetes | ১টি (চাইলে `--nodes=2`) | **Local PC-তে শেখা** (আপনার setup) |

**মনে রাখার trick:**
- **KIND** = Kubernetes **IN** **D**ocker
- **kubeadm** = Kubernetes **ADM**in tool (real cluster)
- **Minikube** = **Mini** Kubernetes (laptop)

## 4.2 Metadata, Labels & Selectors — Kubernetes-এর হার্ট

**English:** Labels are sticky notes you put on resources. Selectors are how OTHER resources find them. Deployment finds its pods by selector; Service finds pods by selector. If labels don't match — nothing connects!

**বাংলা:** Label হলো resource-এ লাগানো স্টিকার। Selector দিয়ে **অন্য** resource-গুলো সেই স্টিকার খুঁজে বের করে। Deployment তার pod খুঁজে selector দিয়ে; Service pod খুঁজে selector দিয়ে। **Label মিল না করলে কিছুই connect হয় না!**

### সম্পর্কের ম্যাপ (আপনার note-এর ASCII স্টাইলে)

```text
┌───────────────── DEPLOYMENT ─────────────────┐
│ metadata:                                     │
│   name: nginx-deployment   ← নিজের নাম         │
│   labels:                                     │
│     app: nginx             ← নিজের label       │
│ spec:                                         │
│   selector:                                   │
│     matchLabels:                              │
│       app: nginx    ─────┐ ← কাকে খুঁজছে       │
│   template:              │                    │
│     metadata:            │                    │
│       labels:            │                    │
│         app: nginx  ◄────┘ ← pod-এ যে label বসবে│
│                          (দুটো মিলা বাধ্যতামূলক) │
└──────────────────────┬───────────────────────┘
                       │ pod তৈরি করে (label: app=nginx সহ)
                       ▼
┌───────────────── SERVICE ────────────────────┐
│ spec:                                         │
│   selector:                                   │
│     app: nginx  ──────────► সেই একই label খুঁজে │
│                             pod-এ traffic পাঠায় │
└───────────────────────────────────────────────┘
```

### তিন জায়গায় `app: nginx` — কেন?

| জায়গা | ভূমিকা |
|---|---|
| Deployment-এর `selector.matchLabels` | "আমি `app: nginx` label-ওয়ালা pod-দের boss" |
| Deployment-এর `template.metadata.labels` | "আমার বানানো প্রতিটি pod-এ `app: nginx` লেবেল লাগাও" |
| Service-এর `selector` | "`app: nginx` লেবেল-ওয়ালা pod-দের কাছে traffic পাঠাও" |

> ⚠️ **সবচেয়ে common bug:** Service-এর selector আর pod-এর label মিলছে না → service-এর কোনো endpoint থাকে না → "connection refused"। Check: `kubectl get endpoints <svc-name> -n <ns>` — খালি দেখালে label মিলছে না বুঝবেন!

### Label দিয়ে খোঁজা (daily debugging trick)

```bash
kubectl get pods -l app=nginx -n ostad          # label দিয়ে pod খোঁজা
kubectl get pods -l app=nginx --show-labels     # label-সহ দেখা
kubectl label pod nginx-pod env=prod -n ostad   # চলমান pod-এ label যোগ
kubectl get endpoints nginx-service -n ostad    # service কোন pod-এ যাচ্ছে দেখা
```

# LESSON 5 — Helm: Kubernetes-এর Package Manager

## 5.1 Helm কী?

**English:** Helm is the package manager for Kubernetes — like `apt` for Ubuntu or `npm` for Node.js. Helm packages are called **charts**. Instead of writing 10 YAML files for MySQL, you run one command: `helm install`.

**বাংলা:** Helm হলো Kubernetes-এর package manager — Ubuntu-র `apt` বা Node-এর `npm`-এর মতো। Helm-এর package-কে বলে **chart**। MySQL-এর জন্য ১০টি YAML না লিখে একটি command: `helm install`।

## 5.2 অন্যের তৈরি Package ব্যবহার (শেখার প্রথম ধাপ)

```bash
# Repository যোগ করা (bitnami = সবচেয়ে বড় chart collection)
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update

# chart খোঁজা
helm search repo nginx
helm search repo mysql

# install (এক command-এ deployment+service+config সব তৈরি!)
helm install my-nginx bitnami/nginx -n ostad

# কী install আছে দেখা
helm list -n ostad

# নিজের value দিয়ে install
helm install my-mysql bitnami/mysql \
  --set auth.rootPassword=secret123 \
  --set auth.database=myapp -n ostad

# uninstall
helm uninstall my-nginx -n ostad
```

| Command | ব্যাখ্যা |
|---|---|
| `helm repo add` | Chart-এর দোকান (repository) যোগ করা |
| `helm install <release-name> <chart>` | Chart install — release-name = আপনার দেওয়া এই copy-এর নাম |
| `--set key=value` | Chart-এর default value override — Docker-এর `-e VAR=x`-এর মতো |
| `helm list` | Install করা release-গুলো দেখা |
| `helm uninstall` | Release-এর সব resource মুছে দেয় — এটাই Helm-এর জাদু, আলাদা আলাদা YAML delete করতে হয় না |

> 💡 **values.yaml ফাইল দিয়ে install (`.env`-এর মতো):** `helm install my-mysql bitnami/mysql -f my-values.yml` — অনেক value একসাথে file থেকে দেওয়া যায়।

## 5.3 নিজের Chart বানানো — মূল Concept

### Chart-এর গঠন

```text
myapp/
├── Chart.yaml              ← chart-এর পরিচয় (নাম, version)
├── values.yaml             ← change-যোগ্য value (.env-এর মতো)
└── templates/              ← আসল YAML-গুলো (variable সহ)
    ├── deployment.yaml
    ├── service.yaml
    ├── configmap.yaml
    ├── secret.yaml
    ├── ingress.yaml
    └── _helpers.tpl        ← reusable variable/function
```

### Value Pass Flow (একদম গুরুত্বপূর্ণ — আপনার note থেকে)

```text
templates/deployment.yaml
      │  {{ .Values.replicaCount }} বা {{ include "myapp.name" . }}
      ▼
values.yaml  ────────────────►  _helpers.tpl
(.Values.*)                     (define হওয়া variable)
                                      │
                                      ▼
                                 Chart.yaml
                                 (.Chart.Name, .Chart.AppVersion)
```

| কে | কার কাছ থেকে value নেয় |
|---|---|
| `templates/*.yaml` | `values.yaml` থেকে (`{{ .Values.xxx }}`) এবং `_helpers.tpl` থেকে (`{{ include "name" . }}`) |
| `_helpers.tpl` | `Chart.yaml` থেকে (`.Chart.Name`) ও install-এর সময়ের release info থেকে (`.Release.Name`) |
| আপনি (user) | Install-এর সময় `--set` বা `-f values.yml` দিয়ে সব override করতে পারেন |

### Step 1: `Chart.yaml`

```yaml
apiVersion: v2
name: myapp
description: A Helm chart for my application
type: application
version: 1.0.0
appVersion: "1.0.0"
maintainers:
  - name: Your Name
    email: you@example.com
```

| Line | ব্যাখ্যা |
|---|---|
| `apiVersion: v2` | Helm 3-এর chart format (v2 ই ব্যবহার করুন) |
| `version: 1.0.0` | **Chart**-এর version (chart বদলালে এটি বাড়ান) |
| `appVersion: "1.0.0"` | ভিতরের **app**-এর version |

### Step 2: `values.yaml`

```yaml
replicaCount: 3

image:
  repository: myapp
  tag: "1.0.0"
  pullPolicy: IfNotPresent

service:
  type: NodePort
  port: 80

resources:
  limits:
    cpu: 500m
    memory: 512Mi
  requests:
    cpu: 250m
    memory: 256Mi
```

### Step 3: `templates/deployment.yaml`

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ include "myapp.name" . }}
  template:
    metadata:
      labels:
        app: {{ include "myapp.name" . }}
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - containerPort: 80
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
```

### Step 4: `templates/_helpers.tpl` (⭐ Main Part — আপনার note অনুযায়ী)

```yaml
{{- define "myapp.name" -}}
{{- .Chart.Name -}}
{{- end -}}

{{- define "myapp.fullname" -}}
{{- printf "%s-%s" .Release.Name (include "myapp.name" .) | trunc 63 | trimSuffix "-" -}}
{{- end -}}
```

| Line | ব্যাখ্যা |
|---|---|
| `{{- define "myapp.name" -}}` | Variable/function declare শুরু — নাম আমরা যা খুশি দিতে পারি |
| `{{- .Chart.Name -}}` | Value আসবে `Chart.yaml`-এর `name:` থেকে |
| `{{- end -}}` | Declare শেষ |
| `{{ include "myapp.name" . }}` | Define করা value **ব্যবহার** করা — শেষের dot (.) = current context পাঠানো |
| `printf "%s-%s"` | String জোড়া লাগানো — প্রথম `%s` = `.Release.Name`, দ্বিতীয় `%s` = chart name |
| `trunc 63` | K8s-এ নাম সর্বোচ্চ ৬৩ অক্ষর — বেশি হলে কেটে দেয় |

**ফলাফল:** `helm install myrelease ./myapp` করলে `myapp.fullname` = `myrelease-myapp` — প্রতিবার unique নাম!

### Step 5: Chart Test ও Install

```bash
helm template ./myapp                        # YAML render হয় ঠিকমতো কিনা দেখা (install ছাড়াই!)
helm lint ./myapp                            # chart-এ ভুল আছে কিনা check
helm install myrelease ./myapp -n ostad      # install
helm list -n ostad
kubectl get all -n ostad                     # কী কী তৈরি হলো দেখুন

helm upgrade myrelease ./myapp -n ostad      # value বদলে update
helm rollback myrelease 1 -n ostad           # আগের revision-এ ফিরে যাওয়া
helm history myrelease -n ostad              # সব revision দেখা
helm uninstall myrelease -n ostad
```

| Command | ব্যাখ্যা |
|---|---|
| `helm template` | ⭐ শেখার সেরা tool — install না করেই final YAML কেমন হবে দেখুন |
| `helm lint` | Chart-এর syntax/structure ঠিক আছে কিনা |
| `helm upgrade` | নতুন value/version দিয়ে update |
| `helm rollback myrelease 1` | ১ নম্বর revision-এ ফিরে যাওয়া — production-এ ভুল deploy-এর প্রাণরক্ষা |

> 🎓 **ক্লাসে শেখানোর পদ্ধতি (আপনার note অনুযায়ী):** প্রথমে bitnami chart install দেখান (package ব্যবহার) → তারপর `helm create myapp` দিয়ে boilerplate বানান → `helm template` দিয়ে দেখান value কীভাবে বদলায় YAML → তারপর নিজেদের app-এর chart লেখান।

# LESSON 7 — HPA (Horizontal Pod Autoscaler)

## 7.1 HPA কী?

**English:** HPA automatically increases/decreases pod replicas based on CPU/memory usage. High load → more pods. Low load → fewer pods. This is what Docker Swarm CANNOT do natively — a key reason people choose Kubernetes.

**বাংলা:** HPA স্বয়ংক্রিয়ভাবে CPU/memory usage দেখে pod-এর replica বাড়ায়/কমায়। Load বেশি → বেশি pod। Load কম → কম pod। Docker Swarm-এ যা নেই — Kubernetes বাছাইয়ের বড় কারণ এটিই।

```text
┌──────────────── HPA Behavior ────────────────┐
│  ┌─────────┐   High Load   ┌──────────┐      │
│  │ 2 Pods  │ ────────────► │ 10 Pods  │      │
│  │  (min)  │               │  (max)   │      │
│  └─────────┘               └──────────┘      │
│       ▲                         ▲            │
│   Scale Down                Scale Up         │
│  CPU < 50%                  CPU > 50%        │
│  (৫ মিনিট অপেক্ষা করে কমায় —                  │
│   fluctuation এড়াতে)                         │
└──────────────────────────────────────────────┘
```

## 7.2 Prerequisite — Metrics Server (HPA এর আগে অবশ্যই!)

```bash
# Minikube-এ:
minikube addons enable metrics-server

# kubeadm/k3s-এ:
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# কাজ করছে কিনা check:
kubectl top nodes
kubectl top pods -n ostad
```

> ⚠️ **HPA কাজ করছে না, `<unknown>` দেখাচ্ছে?** ৯০% ক্ষেত্রে metrics-server নেই বা deployment-এ `resources.requests` দেওয়া নেই। এই দুটোই বাধ্যতামূলক!

## 7.3 Step 1: Deployment (resources সহ — বাধ্যতামূলক)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:latest
        ports:
        - containerPort: 80
        resources:
          requests:          # minimum গ্যারান্টি — HPA এর হিসাব এর উপর হয়
            cpu: "100m"      # 0.1 CPU core
            memory: "128Mi"
          limits:            # সর্বোচ্চ সীমা
            cpu: "500m"
            memory: "512Mi"
```

| Line | ব্যাখ্যা |
|---|---|
| `requests: cpu: 100m` | ⭐ HPA-এর % হিসাব requests-এর উপর হয় — `50%` মানে 100m-এর 50% = 50m ব্যবহার হলে scale শুরু। requests ছাড়া HPA অচল! |
| `100m` | m = millicore; 1000m = 1 CPU core |
| `limits` | Container এর বেশি ব্যবহার করতে পারবে না |

## 7.4 Step 2: HPA তৈরি

### `nginx_hpa.yml`

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-deployment
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
```

### Line-by-Line ব্যাখ্যা

| Line | English | বাংলা |
|---|---|---|
| `apiVersion: autoscaling/v2` | HPA-এর stable API version | HPA-এর API (v2-তেই লিখুন) |
| `scaleTargetRef` | WHICH deployment to scale | কোন deployment-কে scale করবে |
| `name: nginx-deployment` | Target deployment-এর নাম (মিলতে হবে) | Target-এর নাম — deployment-এর নামের সাথে মিলা বাধ্যতামূলক |
| `minReplicas: 2` | Never scale below this | এর নিচে কখনো নামবে না |
| `maxReplicas: 10` | Never scale above this | এর উপরে কখনো উঠবে না |
| `averageUtilization: 50` | Scale up when avg CPU > 50% of requests | গড় CPU requests-এর ৫০% ছাড়ালে pod বাড়াবে |

### CPU + Memory দুটো দিয়েও করা যায়

```yaml
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 50
```

### Scale-Down Behavior (ঝাঁকুনি এড়ানো)

```yaml
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # কমার আগে ৫ মিনিট অপেক্ষা
      policies:
      - type: Percent
        value: 50                        # একবারে সর্বোচ্চ ৫০% pod কমাবে
        periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 0      # বাড়ার সময় অপেক্ষা নেই — সাথে সাথে
```

| Setting | ব্যাখ্যা |
|---|---|
| `stabilizationWindowSeconds: 300` | Load কমলেই সাথে সাথে pod মেরে ফেলবে না — ৫ মিনিট দেখবে সত্যিই কম কিনা। Default-ই ৩০০ সেকেন্ড |
| scaleUp-এ `0` | Load বাড়লে দেরি নয় — তৎক্ষণাৎ pod বাড়ে |

# LESSON 8 — Ingress & Egress

## 8.1 Ingress কী?

**English:** Ingress is the smart HTTP router of Kubernetes — one entry point that routes traffic to different services by domain/path. Instead of a LoadBalancer (expensive) per service, ONE Ingress handles all: `api.myapp.com` → api service, `myapp.com/admin` → admin service. Think of it as Nginx reverse proxy, but Kubernetes-native.

**বাংলা:** Ingress হলো Kubernetes-এর স্মার্ট HTTP router — একটি entry point থেকে domain/path দেখে বিভিন্ন service-এ traffic পাঠায়। প্রতি service-এ আলাদা LoadBalancer (ব্যয়বহুল) না দিয়ে একটি Ingress-ই সব সামলায়। ভাবুন: Nginx reverse proxy, কিন্তু Kubernetes-native।

```text
Internet
   │
   ▼
┌─ Ingress Controller (Nginx) ──────────┐
│  myapp.com/        → frontend-service │
│  myapp.com/api     → api-service      │
│  admin.myapp.com   → admin-service    │
└───────────────────────────────────────┘
```

### দুই জিনিস লাগে (গুরুত্বপূর্ণ!)

1. **Ingress Controller** — আসল router software (Nginx/Traefik) — আগে এটি install করতে হয়
2. **Ingress Resource** — routing rule-এর YAML

```bash
# Minikube-এ controller চালু:
minikube addons enable ingress

# kubeadm-এ:
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/cloud/deploy.yaml

# চলছে কিনা দেখুন:
kubectl get pods -n ingress-nginx
```

## 8.2 Ingress Resource (line-by-line)

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: myapp.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: nginx-service
                port:
                  number: 80
```

| Line | English | বাংলা |
|---|---|---|
| `apiVersion: networking.k8s.io/v1` | Ingress lives in the networking API group | Ingress networking API group-এ থাকে |
| `ingressClassName: nginx` | Which controller handles this (nginx/traefik) | কোন controller এই rule সামলাবে |
| `host: myapp.local` | Domain for this rule — DNS/hosts file-এ point করতে হবে | এই domain-এর request এই rule-এ আসবে |
| `path: /` + `pathType: Prefix` | `/` দিয়ে শুরু হওয়া সব URL match করবে | `/anything` সব match হয় |
| `backend: service: name:` | Traffic যাবে কোন service-এ | Traffic-এর গন্তব্য service |
| `port: number: 80` | Service-এর কোন port-এ | Service-এর port (service-এর `port:`, targetPort নয়!) |

### একাধিক path/host routing (real-world)

```yaml
  rules:
    - host: myapp.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80
          - path: /api

            backend:

                  number: 3000
```

## 8.3 Egress — বাইরে যাওয়ার Traffic

**English:** Ingress = traffic coming IN. Egress = traffic going OUT (pod → internet, e.g. calling external API). By default all egress is allowed; you control it with **NetworkPolicy**.

**বাংলা:** Ingress = ভিতরে **আসা** traffic। Egress = বাইরে **যাওয়া** traffic (pod → internet, যেমন বাইরের API call)। Default-এ সব egress allowed; **NetworkPolicy** দিয়ে নিয়ন্ত্রণ করেন।

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-network-policy
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend        # শুধু frontend pod থেকে আসা allowed
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: mysql           # শুধু mysql-এ যাওয়া allowed
    ports:
    - port: 3306
```

| অংশ | ব্যাখ্যা |
|---|---|
| `podSelector: app: api` | এই rule কার উপর প্রযোজ্য — `api` label-ওয়ালা pod-দের উপর |
| `ingress: from:` | কারা এই pod-এ আসতে পারবে (এখানে শুধু frontend) |
| `egress: to:` | এই pod কোথায় যেতে পারবে (এখানে শুধু mysql:3306) — বাইরের internet বন্ধ! |

> 💡 **Security best practice:** Production-এ database pod-এ NetworkPolicy দিন যাতে শুধু api pod-ই connect করতে পারে — অন্য কেউ (হ্যাকারও) পারবে না।

# LESSON 9 — Deployment Strategies: Rolling Update, Blue-Green & Canary

## 9.1 তিনটি Strategy এক নজরে

```text
Rolling Update (default):
  v1 🟢🟢🟢  →  v1 🟢🟢 + v2 🔵  →  v2 🔵🔵🔵   (একটা একটা করে বদলায়)

Blue-Green:
  v1 (Blue) 🟢🟢🟢 চলছে  +  v2 (Green) 🔵🔵🔵 ready
  → switch: সব traffic একসাথে Green-এ  → সমস্যা হলে instant ফিরে Blue-তে

Canary:
  v1 🟢🟢🟢🟢 (100% traffic)
  → v1 🟢🟢🟢🟢 + v2 🔵 (৫% traffic শুধু v2-এ)
  → ঠিক থাকলে ধীরে ধীরে ২৫% → ৫০% → ১০০%
```

| Strategy | Risk | Rollback | কখন ব্যবহার |
|---|---|---|---|
| Rolling | মাঝারি (একসময় দুই version-ই চলে) | ধীর (`rollout undo`) | সাধারণ app, default |
| Blue-Green | কম (switch-এর আগে test করা যায়) | **তাৎক্ষণিক** (selector বদলে দিন) | গুরুত্বপূর্ণ release, double resource থাকলে |
| Canary | সবচেয়ে কম (অল্প user-এর উপর আগে test) | তাৎক্ষণিক (canary pod মুছে দিন) | বড় userbase, risk-sensitive feature |

## 9.2 Rolling Update (Default) — আগে এটি জানুন

```bash
# নতুন version deploy:
kubectl set image deployment/nginx-deployment nginx=nginx:1.27 -n ostad

# live দেখুন:
kubectl rollout status deployment/nginx-deployment -n ostad

# ভুল হলে rollback:
kubectl rollout undo deployment/nginx-deployment -n ostad

# আগের version-এর history:
kubectl rollout history deployment/nginx-deployment -n ostad
```

| Command | ব্যাখ্যা |
|---|---|
| `kubectl set image ...` | Deployment-এর image বদলায় — K8s নিজেই একটা একটা করে pod বদলায় (downtime নেই) |
| `rollout status` | Update কতদূর হলো live দেখা |
| `rollout undo` | ⭐ আগের version-এ ফিরে যাওয়া — production-এর প্রাণরক্ষা command |

## 9.3 Blue-Green Deployment — Real-Life Step by Step

**Idea:** পুরোনো version (Blue) চলতেই থাকে। নতুন version (Green) আলাদা deployment হিসেবে পুরোপুরি ready করুন। তারপর **Service-এর selector বদলে** সব traffic এক ঝটকায় Green-এ দিন। সমস্যা হলে selector আবার Blue-তে — **instant rollback!**

**চাবিকাঠি:** Service pod বেছে নেয় **label দিয়ে** — তাই selector-এ `version: blue` থেকে `version: green` বদলালেই traffic ঘুরে যায়।

### Step 1: Blue (current v1) deploy করুন

```yaml
# blue-deployment.yml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-blue
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
      version: blue
  template:
    metadata:
      labels:
        app: myapp
        version: blue          # ← এই label-ই switch-এর চাবি
    spec:
      containers:
      - name: myapp
        image: myapp:1.0
        ports:
        - containerPort: 80
```

```yaml
# service.yml — এখন blue-তে যাচ্ছে
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  selector:
    app: myapp
    version: blue              # ← traffic এখন Blue-এ
  ports:
  - port: 80
    targetPort: 80
```

```bash
kubectl apply -f blue-deployment.yml
kubectl apply -f service.yml
kubectl get pods -l version=blue        # ৩টি pod চলছে
```

### Step 2: Green (নতুন v2) deploy করুন — পাশাপাশি, traffic ছাড়াই

```yaml
# green-deployment.yml — শুধু নাম, version label আর image বদলান
metadata:
  name: myapp-green
spec:
  ...
      version: green         # সব জায়গায় (selector + template labels)
  ...
        image: myapp:2.0
```

```bash
kubectl apply -f green-deployment.yml
kubectl get pods -l version=green       # Green ready — কিন্তু কোনো user যাচ্ছে না!
```

### Step 3: Green test করুন (traffic ঘোরানোর আগেই!)

```bash
# সরাসরি green pod-এ port-forward করে ভিতরে ভিতরে test:
kubectl port-forward deployment/myapp-green 9090:80
# Browser-এ http://localhost:9090 — সব ঠিক আছে দেখুন
```

### Step 4: Switch! — সব traffic Green-এ

```bash
kubectl patch service myapp-service \
  -p '{"spec":{"selector":{"app":"myapp","version":"green"}}}'

# Verify:
kubectl get endpoints myapp-service     # এখন green pod-গুলোর IP
```

| Part | ব্যাখ্যা |
|---|---|
| `kubectl patch service` | ⭐ পুরো switch-এর কাজ একটি command-এ — selector বদলে গেলেই সব traffic নতুন version-এ |
| Downtime | প্রায় শূন্য — কোনো pod বন্ধ হয় না, শুধু routing বদলায় |

### Step 5: সমস্যা হলে Instant Rollback

```bash
kubectl patch service myapp-service \
  -p '{"spec":{"selector":{"app":"myapp","version":"blue"}}}'
```

এক সেকেন্ডে আগের version-এ ফিরে গেলেন — কারণ Blue pod-গুলো এখনো বেঁচে আছে!

### Step 6: সব ঠিক থাকলে পরিষ্কার

```bash
kubectl delete deployment myapp-blue    # পুরোনো version মুছে resource ফাঁকা করুন
```

> 💰 **মনে রাখুন:** Blue-Green-এ একসময় **দ্বিগুণ resource** লাগে (৩+৩ = ৬ pod)। ছোট cluster-এ মাথায় রাখুন।

## 9.4 Canary Deployment — Real-Life Step by Step

**Idea:** নতুন version-এর মাত্র ১টি pod চালান — total traffic-এর ছোট অংশ (~১০%) সেখানে যায়। সব ঠিক থাকলে ধীরে ধীরে বাড়ান। **Ratio-ই হিসাব:** ৪টি old + ১টি new = ~২০% traffic new-এ (Kubernetes pod-গুলোতে সমান ভাগে traffic ভাগ করে)।

### Step 1: Stable (v1) চলছে — ৪ replica

```yaml
# stable-deployment.yml (গুরুত্বপূর্ণ: version label থাকবে না — শুধু app label)
spec:
  replicas: 4
  template:
    metadata:
      labels:
        app: myapp
        track: stable
    spec:
      containers:
      - name: myapp
        image: myapp:1.0
```

### Step 2: Canary (v2) — মাত্র ১ replica, একই `app` label!

```yaml
# canary-deployment.yml
metadata:
  name: myapp-canary
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myapp
      track: canary
  template:
    metadata:
      labels:
        app: myapp              # ← একই app label — service দুটোকেই পাবে
        track: canary
    spec:
      containers:
      - name: myapp
        image: myapp:2.0
```

```yaml
# service.yml — শুধু app দিয়ে select (track দিয়ে নয়!)
spec:
  selector:
    app: myapp                  # stable + canary — দুটোর pod-ই পাবে
```

```bash
kubectl apply -f stable-deployment.yml
kubectl apply -f canary-deployment.yml
kubectl apply -f service.yml

kubectl get endpoints myapp-service
# ৫টি IP → ৪টা stable (v1), ১টা canary (v2) = ~২০% traffic v2-তে যাচ্ছে
```

### Step 3: Watch করুন — নতুন version ঠিকমতো চলছে কিনা

```bash
kubectl logs -l track=canary --tail=50 -f     # canary-এর error log দেখুন
kubectl get hpa / metrics দেখুন, error rate, response time monitor করুন
```

### Step 4-A: সব ঠিক থাকলে — ধীরে ধীরে বাড়ান

```bash
kubectl scale deployment myapp-canary --replicas=2    # ২০% → ৩৩%
# আবার দেখুন... তারপর:
kubectl scale deployment myapp-canary --replicas=4
kubectl scale deployment myapp-stable --replicas=0    # পুরোনোটা বন্ধ
kubectl delete deployment myapp-stable                # পরিষ্কার
```

### Step 4-B: সমস্যা দেখা দিলে — instant rollback

```bash
kubectl delete deployment myapp-canary    # canary মুছে দিলেই ১০০% traffic আবার v1-এ
```

| ধাপ | Traffic v2-তে | কাজ |
|---|---|---|
| শুরু | ০% | শুধু stable |
| Canary ১ pod | ~২০% | দেখুন log/metrics |
| Canary ২ pod | ~৩৩% | আবার দেখুন |
| Canary ৪ + stable ০ | ১০০% | সম্পূর্ণ switch |
| যেকোনো সময় সমস্যা | ০% | canary delete — ব্যবসা চলতেই থাকে ✅ |

> 🏭 **Industry তে:** ভালো setup-এ canary automatic হয় (Argo Rollouts / Flagger দিয়ে — error rate বাড়লে নিজেই rollback করে)। কিন্তু উপরের manual পদ্ধতিটি concept বোঝার ভিত্তি — আপাতত এটুকুই যথেষ্ট।

## 10.2 ConfigMap (Nginx + PHP config)

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config
  namespace: laravel-app
```

## 10.3 MySQL Deployment (secret ব্যবহার করে)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mysql
  namespace: laravel-app
spec:
  replicas: 1                        # database সবসময় ১টি
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
      - name: mysql
        image: mysql:8
        env:
        - name: MYSQL_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-secret
              key: mysql-root-password
        - name: MYSQL_DATABASE
          value: laravel_db
        ports:
        - containerPort: 3306
---
apiVersion: v1
kind: Service
metadata:
  name: mysql-service
  namespace: laravel-app
spec:
  type: ClusterIP                  # শুধু cluster-এর ভিতরে — বাইরে expose নয়!
  selector:
    app: mysql
  ports:
  - port: 3306
    targetPort: 3306
```

| অংশ | ব্যাখ্যা |
|---|---|
| `secretKeyRef` | নির্দিষ্ট key secret থেকে env-এ আনা (Lesson 3, পদ্ধতি ৩) |
| `type: ClusterIP` | ⭐ Database বাইরে থেকে access করা যাবে না — security। Docker book-এর "db-তে ports: দেবেন না" rule-এর K8s রূপ |
| Laravel-এর `.env`-এ | `DB_HOST=mysql-service` — service name-ই hostname |

# LESSON 11 — Debugging Skills + Daily Cheat Sheet

## 11.1 Pod ঠিকমতো চলছে না? — নির্দিষ্ট Diagnosis ক্রম (মুখস্থ রাখুন)

```bash
# ধাপ ১: অবস্থা দেখুন — STATUS column-এ কী লেখা?
kubectl get pods -n <ns>

# ধাপ ২: বিস্তারিত + EVENTS (সবচেয়ে গুরুত্বপূর্ণ — ৮০% উত্তর নিচে Events-এ!)
kubectl describe pod <pod-name> -n <ns>

# ধাপ ৩: Application-এর log
kubectl logs <pod-name> -n <ns>
kubectl logs <pod-name> -n <ns> --previous      # আগের (crash হওয়া) container-এর log

# ধাপ ৪: ভিতরে ঢুকে দেখুন
kubectl exec -it <pod-name> -n <ns> -- sh
```

### STATUS অনুযায়ী রোগ নির্ণয় Table

| STATUS | মানে | সমাধান |
|---|---|---|
| `ContainerCreating` এ আটকে | Image নামছে বা volume mount হচ্ছে না | `describe` দেখুন — image name ভুল? bind/PVC আছে? |
| `ImagePullBackOff` / `ErrImagePull` | Image পাওয়া যাচ্ছে না | Image-এর নাম/tag ঠিক আছে? Private হলে registry login (imagePullSecret) আছে? |
| `CrashLoopBackOff` | Container চালু হয়েই বারবার মরে যাচ্ছে | `kubectl logs --previous` দেখুন — app-এর error, env variable, DB connection check |
| `Pending` | কোনো node-এ বসানো যাচ্ছে না | Resource (CPU/RAM) requests বেশি? Node-এ জায়গা আছে? `describe`-এ লেখা থাকবে |
| `Running` কিন্তু কাজ করছে না | App চলছে কিন্তু ভুলভাবে | Service selector আর pod label মিলছে? → `kubectl get endpoints <svc>` খালি কিনা দেখুন |

### আরও ৩টি ভাইরাল সমস্যা (আপনার note থেকে)

| সমস্যা | কারণ | সমাধান |
|---|---|---|
| Node `NotReady` (kubeadm) | Network plugin দেওয়া হয়নি | Calico/Flannel apply করুন (Lesson 6, Step 4) |
| HPA-এ `<unknown>` | metrics-server নেই বা `resources.requests` দেওয়া নেই | দুটোই ঠিক করুন (Lesson 7.2–7.3) |
| `kubeadm join` token কাজ করছে না | Token-এর ২৪ ঘণ্টার মেয়াদ শেষ | `kubeadm token create --print-join-command` |

## 11.2 Daily Cheat Sheet

```bash
# ─── দেখা ───
kubectl get all -A                          # সব cluster-এর সব কিছু
kubectl get nodes                           # node-গুলো
kubectl get pods -n <ns> -o wide            # কোন node-এ কোন pod
kubectl top nodes / kubectl top pods -A     # CPU/RAM usage

# ─── Debug ───
kubectl describe pod <name> -n <ns>         # EVENTS — প্রথমেই এখানে তাকান
kubectl logs <name> -n <ns> -f              # live log
kubectl get events -n <ns> --sort-by=.metadata.creationTimestamp

# ─── কাজ ───
kubectl apply -f file.yml                   # তৈরি/update
kubectl delete -f file.yml                  # মোছা
kubectl scale deployment <name> --replicas=5 -n <ns>
kubectl rollout undo deployment/<name> -n <ns>    # rollback

# ─── ভিতরে ঢোকা ───
kubectl exec -it <pod> -n <ns> -- sh
kubectl port-forward svc/<name> 8080:80 -n <ns>

# ─── Minikube ───
minikube service <name> -n <ns>             # browser-এ খোলে
minikube tunnel                             # LoadBalancer-এর জন্য
minikube ssh                                # minikube node-এর ভিতরে
```

## 11.3 Docker vs Kubernetes — সমতুল্য Table (আপনার background থেকে দ্রুত বোঝার জন্য)

| Docker / Swarm | Kubernetes |
|---|---|
| `docker run` | Pod (Deployment দিয়ে) |
| `docker service` + replicas | Deployment + ReplicaSet |
| `docker service scale` | `kubectl scale` / HPA (auto!) |
| `-p 8080:80` | Service (NodePort/LoadBalancer) + `port-forward` |
| `--env-file .env` | ConfigMap (`envFrom`) |
| Docker secret | Secret |
| Volume (`-v`) | volumeMounts + volumes / PVC |
| Stack (এক project) | **Namespace** |
| docker-compose.yml | Helm Chart |
| `docker logs` | `kubectl logs` |
| `docker exec -it` | `kubectl exec -it` |
| Traefik/Nginx reverse proxy | Ingress |
